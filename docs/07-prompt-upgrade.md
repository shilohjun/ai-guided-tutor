# 回答规范升级与验收说明

本次改动只提交到 yangshuhan，供组员评审。没有修改前端页面、部署服务或合并 main。

## 解决了什么

| 原来的冲突或缺口 | 本次处理 | 位置 |
|---|---|---|
| 一句话、长复述和额外下一步叠加，字数口径不一致 | 通常两至三行，整条回复尽量60–100字，绝不超过150字；诊断复述留在内部 | llm.js、prompt.js、response-policy.js |
| L1/L2一律禁公式，和学生忘记公式时需要提醒冲突 | 可以提醒适用的通用公式及条件；题目最终结果式与既有指纹禁区仍拦截 | llm.js、guard.js |
| 模型没有收到此前提示，难以做到实质递进 | 传入最近十轮对话和本轮原话；增加三级正例、反例和新增信息要求 | llm.js、engine.js |
| 只检查正文，下一步可能泄题或让整条消息超长 | text与nextAsk组装后统一检查；无效JSON重试，不直接展示原始模型输出 | engine.js |
| 删除公式或截短可能丢失条件 | 不再采纳守卫的删式子、截断结果；完整重新生成一次 | engine.js |
| 全会话提示等级混在一起，新步骤可能直接到L3 | 按路径、步骤、卡点统计已交付提示；确认、拒绝、静默与兜底不支撑升级 | route.js、router.js |
| “还是不会”可能被重新诊断为新卡点 | 同位置的简短追问继承卡点，原历史保留 | engine.js |
| 自主训练遇到高置信卡点会主动提示 | 未主动求助时仍保持静默 | route.js |
| 内部观察不许记学生自己写的结果、证据允许只匹配前六字 | 可忠实记录未核实陈述；证据必须完整匹配归一化原话子串 | llm.js |
| 观察接口失败被当成学生没思路 | 返回503、retryable=true；不写入学习历史 | engine.js、router.js |
| 飞书规范和源码可能各改各的 | 文档直接从运行时提示词导出，有同步检查命令 | scripts/export-prompts.js |

## 输出约定

模型返回现有JSON字段，接口结构不另起一套：

```json
{"text":"一个具体方向，必要时含公式与条件。","nextAsk":"一个学生能独立完成的小任务。","concepts":["对应知识点"]}
```

页面显示“提示：…”和“试一试：…”。text内可加“公式：…”一行。通常两至三行，不强制用空话凑满60字。单问号不等于单任务：代码只能检查明显多问句，多个动作藏在一个问号里仍须人工评审。

生成失败两次时保留既有安全兜底，并标记form=fallback；兜底也要通过整条检查，不计作已交付分层提示。若题目概念错误地含结果式，使用不带物理推断的故障说明。兜底不是“成功理解题目”的证明。

## 案例集怎么补

每个案例按“题目＋当前步骤＋学生卡点”组织，而非只收一段好回答。建议表头：

| 字段 | 用途 |
|---|---|
| case_id、version、split（dev/test） | 追踪版本、隔离开发案例与独立测试 |
| question_id、stem、已知条件、图示说明 | 让回答有真实题意依据；图片须人工确认文字转写 |
| 标准解法、步骤划分、最终结果禁区 | 留服务端，帮助教研核实物理正确与泄题边界 |
| 当前step_id、student_message、previous_hints | 确认卡点，避免脱离历史或重复提示 |
| L1、L2、L3的text/nextAsk/concepts | 分别示范方向、具体提示、当前一步解析 |
| added_information、allowed_local_step | 写清每级新增信息及允许讲到哪里 |
| bad_reply、why_bad | 标明啰嗦、空泛、重复、错误公式或泄题等反例 |
| reviewer、review_status、source | 追踪物理老师审核与来源；不是AI写完就自动通过 |

组员先用表格填写，开发再按上述字段转JSONL（每行一个完整JSON案例）；同题的三层回答放同一split，避免同题泄入独立测试。只把审核通过、与当前知识点和卡点匹配的少量正例接入提示；反例须带“禁止模仿”和原因。不要把全题答案附在学生可见提示里。此分支没有接入RAG，也没有把之前的独立测试案例塞入运行时提示。

## 验证方式

```text
npm test                    原有272项检查
npm run test:reply-policy   新增17项回答策略回归
npm run prompts:check       规范与源码同步检查
npm run eval                19个场景的离线机制评测
```

本次验证不调用付费模型：新增17项通过；原套件265/272通过，与改动前一致。七项既有失败为拍照入口、识别可用性标签、DOM引用、学生页教研内容、教师页面容器、模式控件与模式文案；没有删掉、跳过这些失败，也没有修改组员的页面去凑通过率。

离线评测是19场景39轮的规则桩检查，泄题、跳级、解法倾倒、崩溃均为零。它不是实际模型准确率。离线定位命中率92.9%、可行动率56.4%，说明教学内容仍有改进空间，不能声称“已解决所有准确性问题”。

## 组员下一步需要确认

1. 由物理老师审核本次三级范例与禁区。旧题库可能把中间公式也列为禁区，当前仍保守拦截；需逐题区分通用知识、允许的局部步骤与最终结果，不能全局关闭守卫。
2. 用同一模型配置分别跑旧版和新版，以及一组不参与写提示的题目；记录原始回复、字数、卡点判断、三级新增信息、公式条件、泄题及兜底率。重复跑几次观察稳定性。
3. 字数、格式、已知指纹只能检查部分问题；实质递进、公式适用性和错误推理需要教师评价。图片识别不清或题目条件缺失时应先澄清，读题流程的可靠性需单独验收。
4. 先完善审核案例和上述评测，再考虑接入RAG。RAG建议收教材知识点、公式条件、常见误区和审核过的局部提示；不要把网上整题答案直接当学生提示检索库。

规则与示例分离的组织方式参考 [OpenAI官方提示词指南](https://developers.openai.com/api/docs/guides/prompt-engineering)。没有更换团队模型或API协议。
