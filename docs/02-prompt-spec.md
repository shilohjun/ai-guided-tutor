# Prompt 规范

> 本文档是提示词的**评审标准与设计说明**。
> 可执行版本在 `src/core/llm.js`（`OBSERVE_SYSTEM_PROMPT` / `DRAFT_SYSTEM_PROMPT`）。
> 两者必须同步；改动提示词时请一并更新本文档的"变更记录"。

---

## 一、总体原则

### 1.1 提示词只做"能力"，不做"分寸"

本项目把模型能力限制在两个明确边界内：

```
✅ 模型负责：把学生的话读懂（observe）
✅ 模型负责：在指定层级内把话写好（draft）
❌ 模型不负责：判断学生卡在哪一步      → 双通道交叉校验
❌ 模型不负责：决定给几级提示          → 规则引擎
❌ 模型不负责：判断什么算"给了答案"    → 出口守卫
```

**为什么这样切**：Prompt 是概率性的，规则是确定性的。
凡是"错了会很严重"的判断（层级、泄题），都必须是确定性的。

### 1.2 提示词规范的三条硬要求

| 要求 | 原因 |
|---|---|
| 必须声明**禁止事项**，并给出**反面例子** | 只说"不要给答案"，模型不知道边界在哪 |
| 必须要求**证据引用**（学生原话子串） | 让幻觉定位无法通过校验 |
| 必须要求**结构化输出**（JSON） | 让下游能用代码校验，而不是靠文本解析 |

## 二、OBSERVE 阶段：把学生思路转成结构化观察

### 2.1 系统提示词（当前版本）

```
你是物理教研助手的"思路听写员"。你的唯一任务是把学生说的解题思路转写成结构化观察。

【你的身份边界】
你不是解题者，不是老师，不评价对错。你只做三件事：记录、归类、指认位置。

【绝对禁止】
1. 禁止出现任何数值计算结果（如 "0.4 V"、"1 A"、"4 m/s"）。
2. 禁止给出任何公式的最终形式（不要写 "E = BLv"、"I = E/(R+r)"）。
3. 禁止给出答案、结论、或"所以应该…"。
4. 禁止编造学生没说过的话。evidenceQuotes 里的每一句必须是学生原话的子串。

【输出格式】只输出一个 JSON 对象，不要多余文字、不要 markdown 代码块：
{
  "knowns": [...],
  "goal": "...",
  "laws": [...],
  "reasoningChain": [...],
  "uncertainties": [...],
  "stuckPoint": "...",
  "hasComputationTrace": true/false,
  "candidateStepIndex": 数字或 null,
  "candidateMisconceptionIds": [...],
  "evidenceQuotes": [...],
  "restatement": "..."
}
```

### 2.2 设计说明

**为什么叫"听写员"而不是"老师"**：
角色名会强烈影响模型行为。叫"老师"它会忍不住开始讲题；
叫"听写员"它才会专注在"记录学生说了什么"。

**为什么 observe 阶段禁止出现公式**：
这个阶段的输出会成为下游 prompt 的一部分。如果 observe 阶段就把
`I = E/(R+r)` 写进 `laws`，draft 阶段几乎必然会把它抄进提示里。
**在源头掐断比在下游拦截便宜得多。**

**为什么强制 `evidenceQuotes` 必须是原话子串**：
这是防幻觉定位的唯一实际手段。代码里有强校验：

```js
const quotes = asArray(parsed.evidenceQuotes).filter((q) => {
  const q2 = normalize(q);
  if (!q2) return false;
  if (utterance.includes(q2)) return true;
  return q2.length >= 6 && utterance.includes(q2.slice(0, 6));  // 容忍轻微改写
});
```

编造的引用会被静默丢弃；没有引用支撑的定位会被降置信，退化为"先澄清"。

### 2.3 用户提示词结构

```
【题目】<题干>

【标准解题路径图谱（仅供你对齐位置，不要抄给学生）】
路径【路径名】(id=...)
  前提: 前提一 / 前提二
  步骤:
    1. [kind] 步骤标题 —— 该步意图
    ...

【已知的常见错因清单（只能从这里选 id）】
  - id=... | 错因标签 | 学生典型说法: ...

【本轮之前的对话】
学生: ...
AI(L1): ...

【学生本轮的原话】
<原话>

请输出 JSON 观察结果。再次强调：不要出现任何数值结果和公式表达式。
```

**关键点**：

- 图谱以**文字大纲**形式给出，不是 JSON。
  实测 JSON 会让模型倾向于"复述数据"，文字大纲更利于它做对齐判断。
- 错因清单有明确边界（"只能从这里选 id"），
  否则模型会自创错因，导致下游 `misconceptions.find()` 返回 undefined。
- 对话历史带上了 AI 轮次的层级（`AI(L1):`），
  这让模型知道"已经提示到哪一级了"，避免它重复或越级。

## 三、INTAKE 阶段：把一道新题读成结构化题目

> 时序上这是**第一步**（读题 → 观察学生 → 起草提示），
> 但它比 OBSERVE / DRAFT 晚一步实现，所以排在文档第三节。
>
> 代码：`INTAKE_SYSTEM_PROMPT` / `buildIntakeUserPrompt`（`src/core/llm.js`），
> 归一化与降级在 `src/core/intake.js`。

### 3.1 这一阶段要产出什么

| 产出 | 用途 | 缺了会怎样 |
|---|---|---|
| `topics` | 学生版知识图谱的节点来源 | 学生看不到这道题考什么 |
| `givens` / `asked` | 解析面板的关键变量；提示里引用题干 | 提示无法引用具体条件，只能空谈 |
| `fields: keyConditions` | 解析面板"关键条件" | 解析退化成知识点罗列 |
| `knowledgeGraph` | 知识图谱的节点与关系 | 关系只能按文本派生（会标 `derived`） |
| `solutionGraphs[].steps[].cues` | **关键词定位通道的唯一输入** | 双通道交叉校验退化成单通道，模型一错就全错 |
| `answerFingerprints` 等三组指纹 | **守卫的比对基准** | 守卫对这道题等于不存在（见下） |

最后一行是这一阶段最容易被低估的：题目是现场生成的，
**没有指纹的题目对守卫是不可见的**。所以提示词里把三组指纹写成"必填"，
归一化层再做三道兜底（模型给 → 从参考答案反推 → 仍然缺失就记 warning 并在教师视图显示）。

### 3.2 系统提示词（当前版本）

```
你是中学理科教研员，任务是读题建档：把一道题目转写成结构化的"解题路径图谱"，
供后续的引导引擎使用。

【你的产出会怎么被使用】
1. 学生看到的只有题干原文，不会看到你写的路径。
2. 引擎会拿你写的 steps[].cues 去匹配学生的话，所以 cues 必须是学生会真的说出口的词。
3. 引擎会拿 answerFingerprints / formulaFingerprints / solutionInsights
   当"不许说出口"的黑名单。这三项写漏了 = 守卫对这道题失效 = 可能泄题。

【读题要求】
- 路径要写成"动作"，不要写成"公式抄写"。
- 一题允许多解；只有一条就给一条，不要硬凑。
- 每一步的 kind 只能从这七个里选：
  setup / identify / precondition / apply / derive / interpret / conclude
- cues 每步给 3~6 个，每个 2~8 个字，是学生口语里会出现的说法。

【指纹（必填，写错等于守卫失效）】
- answerFingerprints：最终答案的数值+单位（正则）。
  ⚠️ 不要把题干已给的已知量写进来 —— 那会让引擎连"引用题干"都拦掉。
- formulaFingerprints：核心解法公式的完整表达式（正则）。
- solutionInsights：一句话说破就毁掉整道题的结论。
  判据是"指派"而非"提及"：说"这个量扮演什么角色"要拦，问"它扮演什么角色"不拦。

【绝对禁止】
1. 不要输出任何面向学生的讲解、鼓励、评语。你只建档。
2. referenceAnswer 里写完整解法（服务端内部），但不许把它写进 topics / step 标题。
3. 题干不要改写，原样保留。

【keyConditions 与 knowledgeGraph 的额外要求 —— 它们是给学生看的，标准更高】
- keyConditions 里必须有一条是"最容易被学生忽略但最关键"的那个定性条件。
  如果 meaning 会直接把答案说破，就在 ask 里写成一句让学生自己翻译的提问。
- knowledgeGraph 只放章节级知识点，**不要把解题步骤里的概念放进来** ——
  那些属于解法，不是知识点。role=core 最多 2 个。
```

（完整版含 JSON schema，见 `src/core/llm.js`。文档里不重复 schema 是刻意的：
schema 抄两遍一定会漂移，而那正是"提示词与实现不一致"这类 bug 的来源。）

### 3.3 设计说明

**① 为什么连"读题"也要结构化，而不是让模型直接讲这道题。**
因为下游（定位、守卫、报告）全部是拿 `Problem` 当基准做确定性判断的。
读题如果产出的是自然语言，就等于把整套确定性机制架空。

**② 为什么在提示词里反复强调 cues。**
cues 是关键词定位通道**唯一**的输入。一条路径如果没有 cues，
定位就 100% 依赖模型通道，而双通道交叉校验会退化成单通道 ——
模型一旦误判就没有第二意见。这正是"错误的提示比不给提示伤害更大"的场景。
归一化层因此还会从标题 / 概念里派生补齐 cues（见 `intake.js` 的 `ensureCues`）。

**③ 为什么把"别把已知量写进指纹"写在提示词里，而不是只靠代码兜底。**
因为代码兜底（`dropFingerprintsMatchingStem`）只能救"能匹配题干"的指纹；
模型如果写了一条"看起来像答案、其实题干没出现过"的过宽指纹，代码救不了。
提示词是**第一道**，代码是**第二道** —— 两道都要有。

**④ 三个阶段的模型分工是同一句话。**

| 阶段 | 模型做 | 代码做 |
|---|---|---|
| INTAKE | 读懂**题目** | 校验结构、补齐 cues、三道指纹兜底 |
| OBSERVE | 听懂**学生** | 双通道交叉校验、信息不足改反问 |
| DRAFT | 说好**一句话** | 定层级、过守卫、voice 关 |

**模型负责"懂"，代码负责"分寸"。** 三个阶段是同一条切法。

## 四、DRAFT 阶段：在指定层级内写提示

### 4.1 系统提示词（当前版本）

```
你是中学物理的引导型老师。你的任务是根据诊断结论，写出"恰好卡在指定层级"的一句提示。

【最高原则】
你是在帮学生自己想出来，不是替他想。学生看完你的话，必须还需要自己动脑才能往前走。

【层级定义 —— 你本轮被指定了唯一层级，越级即失败】
L0 结构化澄清：学生还没形成思路。你只能帮他把已知/目标/困惑说清楚，或反问一个开放式问题。不得含任何物理方向。
L1 条件追问：只提问，不指方向。问"某个规律的前提条件是什么""这个信息在力学里意味着什么"。
    反面例子（禁止）："你可以用动量定理" ← 这是 L2
    正面例子："题目特意说'匀速'，这个信息在力学里对应什么条件？"
L2 方向提示：指出该关注哪个量/哪个关系/哪个模块，但仍不给公式、不给量之间的关系式。
    正面例子："力的大小和电流有关，而电流又和速度有关，先想想这两个'有关'是怎么连起来的。"
L3 降级示范：示范一个"动作"——选研究对象、写守恒式左边、做一步代数变形。仍不得给出数值结果。
    正面例子："我们先只写左边：恒力的冲量该怎么写？右边是动量变化，你先写出这两项的符号形式。"

【绝对禁止（任何层级都不许出现）】
1. 不许出现本题的最终答案或其数值（包括"大约是0.4""接近1"这类）。
2. 不许给出待求量的完整表达式（如 v_max = F(R+r)/(B²L²)）。
3. 不许列出完整解题步骤序列（超过 2 步就违规）。
4. 不许出现"所以答案就是""最终结果""因此可得…"这类收口句式。

【输出格式】只输出一个 JSON：
{ "text": "...", "nextAsk": "...", "concepts": [...] }
```

### 4.2 设计说明

**为什么每个层级都配"正面例子"和"反面例子"**：
只给定义时，模型对"是不是越级"的判断很不稳定。
**反面例子是最有效的边界信号** —— 尤其 L1 的反面例子
（"你可以用动量定理"← 这是 L2）直接告诉它"点名规律就算越级"。

**为什么 `nextAsk` 是独立字段**：
"提示"和"下一步动作"是两件事，但模型很容易把它们揉成一句，
结果是"既没提示清楚，也没说清要做什么"。
拆成字段后，UI 也能用不同颜色渲染（`【下一步】` 前缀）。

**为什么强调"平方之后再取平均"这类具体边界**：
模型在 L2 层最容易犯的错是"给了一个量之间的关系式"。
提示词里必须有"仍不给关系式"的明确表述，配合守卫的 `formula_leak` 检查形成双保险。

### 4.3 用户提示词结构

```
【题目】<题干>

【学生当前状态（内部信息，不要复述给学生）】
- 已定位到：路径「...」第 N 步 —— 步骤标题
- 定位置信度：0.90
- 卡点性质：precondition_gap
- 判定错因：...
- 学生不确定处：...

【本轮指定层级】L1
【本轮策略】<策略说明>
【可以引用的概念白名单】...
【必须回避的内容】...
【该步的知识位置提示】这一步的"动作类型"是 apply，涉及概念：...
```

**"必须回避的内容"是动态闭环**：
守卫把上一轮拦下的违规反推成禁止项，注入下一轮 prompt：

```js
for (const v of pastViolations) {
  forbidden.push(`上一轮被拦截：${v.kind} —— ${v.detail}`);
}
```

这让"守卫拦什么，模型下一轮就回避什么"形成闭环，
比单纯重试一次有效得多。

## 五、Prompt 与守卫的分工边界

这是评审时最常被问到的问题：**既然有守卫，Prompt 还需要写那么细吗？**

| 维度 | Prompt | 守卫 |
|---|---|---|
| 性质 | 概率性引导 | 确定性保证 |
| 作用 | 让**大多数**输出直接合格 | 让**所有**输出必然安全 |
| 失效后果 | 多一次重写（体验略差） | —— |
| 反向作用 | —— | 防止重写把提示改成"什么都没说" |

**两者都必须有**：

- 只有守卫没有细 Prompt → 大量提示被拦 → 频繁走兜底模板 → 提示千篇一律
- 只有 Prompt 没有守卫 → 迟早有一次泄题，而**一次就够了**（学生截图发群）

实测数据（离线桩 + 恶意模型模拟）：

```
恶意适配器每轮都故意泄题 → 守卫拦截率 100%，最终交付泄题率 0%
```

## 六、变更记录

### v0.5 的事故记录（离线桩阶段）

**现象**：对"导体棒匀速切割、学生漏了内阻"这道题，AI 在 L2 层回复：

> "换个角度看：现在你手上缺的是一个能'跨时间累积'的量。想想哪个定理专门处理这类量。"

这是**动量定理**的话术，与本题（纯电路问题）毫无关系。

**根因**：不是 Prompt 的问题，而是离线桩的 L2 模板**硬编码了这套话术**。
但它暴露了一个系统性问题：**当时没有任何机制能发现"提示跑题"**。

**修复**（三层）：

1. **模板层**：L2/L3 改为从**当前步骤自身的概念与前提**派生，不再用固定话术
2. **守卫层**：新增 `concept_out_of_domain` 检查（封闭词表 + 题目领域文本比对）
3. **测试层**：新增断言，禁止提示中出现本题领域外的物理概念

**教训**：泄题会被守卫拦住，**跑题不会** ——
但跑题同样致命，因为学生会立刻发现"AI 没看懂我的题"，产品的可信度直接归零。

### v0.6 / v0.7 的事故记录（真模型阶段）

这两条**只有跑真模型才能发现** —— 离线桩的输出来自不含答案的模板，
永远不会"说漏嘴"，也不会漏报错因。详见
[`03-evaluation-spec.md`](03-evaluation-spec.md) §八。

**v0.6：模型漏报错因**

学生在"把变加速当匀变速"这道题上说"a=F/m 是恒定的"，
错因清单里明明是 `m-uniform-accel`，模型却报了空数组。

**根因**：原提示词只说"从给定错因清单里选"，没有要求"逐句比对"。
模型倾向于只在他认为"明显错"时才报，而学生的错往往说得很流畅。

**修复**：在 observe 提示词里新增一段判定要求，明确：
- 把每一句话都与清单逐条比对，**只要有一句符合就选中**
- 特别留意三类信号：理由错但结论对 / 把量当常量 / 说"直接""不用管"某量
- **宁可多报一条也不要漏报**（多报会被后续校验筛掉，漏报无法补救）

> "宁可多报"这个方向是刻意选的：误报的成本是"提示不够精准"（可被守卫与路由纠正），
> 漏报的成本是"对着错误的步骤给提示"（学生会困惑）。

**v0.7：模型说出解题核心结论**

真模型在 L1 层回复：

> "电阻 R 和导体棒自身的电阻 r 组成了外电路和内阻。"

没有公式、没有数值、没有收口句式 —— 原有 6 类检查全部放行，
但学生漏的正是"导体棒有内阻"。

**修复**：新增 `solution_insight` 检查（L0–L2 生效），判据是"指派"而非"提及"。
同时这也**反推改进了提示词**：把"不许给数值/公式"扩展到
"不许替学生下结论"，并在 draft 提示词里明确"你是在帮学生自己想出来"。

**教训**：Prompt 与守卫是**互相发现**的 ——
守卫拦下什么，暴露出 prompt 在哪个方向上表述不足；
而 prompt 表述充分后，守卫的拦截率会下降（但仍必须保留）。

### v0.8 的新增：INTAKE 阶段（读题提示词）

新增第三个阶段（§三）。触发原因是产品范围变了：
题库时代"图谱由教研手写"，一旦支持任意题目，图谱就必须现场生成 ——
而守卫是拿图谱当比对基准的，**没有指纹的题目对守卫是不可见的**。

这一轮踩到的两个坑（都已固化进测试）：

1. **模型把题干里的已知量写进了 `answerFingerprints`。**
   它把"落地前 1 s 内"的 `1 s` 当成答案指纹，于是引擎连题目里的那 1 秒都不许说，
   所有提示被拦成兜底模板。表现形式不是"泄题"，而是"AI 又笨又啰嗦" ——
   这类故障比泄题更难被发现。
   修法：`dropFingerprintsMatchingStem()` —— **一个能匹配题干的指纹，不可能是答案**。

2. **解析里的"关键条件含义"会把前提说破。**
   见 §五末尾对 `doesReveal` 的说明，以及 `docs/04` §5.2。

### v0.9 的调整：DRAFT 提示词加"说话方式"一节

原 DRAFT 只约束"层级与禁止事项"，不约束**怎么说话**。真模型因此经常产出：
一句里问两个问题、空洞的鼓励（"加油""相信你可以的"）、不引用学生说过的任何词。

新增三条硬约束（一次只问一个问题 / 不评判 / 必须引用学生自己说过的词），
外加代码层的 voice 关（`polishVoice()`）—— 空话由代码删除，不靠模型自觉。

| 版本 | 变更 | 原因 |
|---|---|---|
| v0.1 | 初版三阶段提示词 | —— |
| v0.2 | observe 阶段新增"禁止出现公式" | observe 输出的公式会被 draft 抄走 |
| v0.3 | draft 阶段每层配反例 | 只给定义时"是否越级"判断不稳定 |

| v0.5 | 守卫新增概念域检查（跑题） | 实测发现 L2 模板会让模型聊起本题无关的概念 |

## 七、外部设计对照的采纳记录

参考过一份外部设计稿的三段提示词。**结论是：Prompt 写"违反即失败"管不住模型** ——
实测真模型在 39 轮里仍越界 6–11 次，最终必须靠出口守卫兜住。
但那份设计里有两点比我们原来的做法好，已采纳并实现：

### 采纳一：`信息是否充足` 开关（原设计称"信息是否充足"）

**它指出的问题**：学生说"我不会""不知道"时，不该硬判。

**我们原来的缺陷**：无论学生说什么都要给一个诊断结论，
哪怕他只说"我不会"，也要硬给一个 `stepIndex` 和错因 —— 只是把置信度压到 0.2。
**编出来的定位比没有定位更糟**：学生会立刻认为"这个 AI 在瞎说"。

**实现**（`Diagnosis.sufficientInfo` + `probeQuestion`）：

- `sufficientInfo === false` ⇒ 不做定位判断，改出 `probeQuestion`
- 反问轮的**概念白名单为空**（没有概念可引用 ⇒ 模型无法给方向）
- 两个必须注意的约束：
  1. 判定基准是**学生发言本身**，不能从 `reasoningChain` / `knowns` 反推
     （离线桩会把任何发言粗切成推理链，"我不会"也能切出一段）
  2. **有历史语境时不走反问** —— 已说过思路的人再说"我不会"属于追问继承，
     应按原定位继续升级

### 采纳二：`走对的部分`（原设计称"走对的部分"）

**它指出的问题**：应该先告诉学生他想对了什么。

**我们原来的缺陷**：内部有 `completedSteps` 和可行性判定，
但**从不告诉学生"你想对了哪些"**。一个卡住的学生最需要先听到这句。

**实现**（`Diagnosis.strengths`）：来源全部可验证，不做主观评价 ——
① 他用对的规律（且该规律确实在标准路径上）；
② 已走过的步骤。放在复述段里、卡点之前。

### 未采纳的部分及理由

| 原设计 | 为什么没有照搬 |
|---|---|
| 靠 prompt 声明"违反即失败" | 实测拦不住：真模型 39 轮里越界 6–11 次。必须配出口守卫 |
| 第 3 层"只示范一小步（不超过一行）" | "一小步"的边界模型自己判不准，实测会顺手示范第二步。我们改为**按步骤类型固定示范动作**（`apply` 只允许写式子左边） |
| 由模型决定给第几层 | 学生会一喊难就拿到最强提示。层级必须由规则引擎决定，并加"禁止跳级"护栏 |
| 靠 prompt 里的"已经给过的提示"防重复 | 实测会重复。改为在代码里按"同一卡点 + 同一层级"计数 |
| 标准解题路径用线性列表 | 线性列表表达不了分支：`f = μN` 只在有摩擦时才进入。改用带 `preconditions` 和 `kind` 的图谱 |

### 一个更深的教训

那份设计里"任务 1 · 整理学生思路"和"任务 3 · 分层给提示"是**同内容**，
且没有区分"观察"与"决策"两层。我们一开始也犯过同样的错 ——

**把"该给几级提示"和"什么算给了答案"留在模型手里，是这类系统最常见的结构性缺陷。**
模型负责"懂"，代码负责"分寸"。

## 八、评审检查清单

评审或修改提示词时，逐条对照：

- [ ] 是否明确声明了**身份边界**（你不是什么）？
- [ ] 是否有**绝对禁止**清单，且带具体例子？
- [ ] 是否要求**结构化输出**，并有下游校验？
- [ ] 是否强制**证据引用**（可指回原文）？
- [ ] 每个层级是否都有**正例与反例**？
- [ ] 是否包含**输出长度的隐性约束**（防止倾倒）？
- [ ] 是否把"决策"完全排除在模型职责之外？
- [ ] 改动后是否重跑了 `node test/run.js` 与 `node scripts/eval.js`？
- [ ] 安全指标是否仍全部为 0？（泄题 / 跳级 / 确认答案 / 解法倾倒 / 崩溃）
