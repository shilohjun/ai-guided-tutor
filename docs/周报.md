**周期**：本周
**阶段**：核心能力 PoC 完成，已在真实大模型上验证，代码与演示均已公开

## 一、总体概述

### 1.1 一句话说明这个项目在做什么

现在所有学习产品的入口都是「学生提问 → AI 回答」，AI 主要通过最后的答案判断学生的问题。
我们把这个方向反过来：**让学生先交出自己的思路，AI 看懂他卡在哪一步，然后只给提示、不给答案。**

方向一变，立刻产生一个全新的技术难题：

> **怎么保证 AI 在"帮"学生的同时，绝不把答案说出去？**

本周的全部工作都围绕解决这个问题展开。

### 1.2 技术栈

| 层次 | 选型 | 为什么这么选 |
|---|---|---|
| **运行时** | Node.js ≥ 20（原生 ESM） | 零依赖即可运行，方便交到教研/企业手里直接跑 |
| **第三方依赖** | **0 个**（不用 Express、不用任何框架） | 企业内网环境 `clone` 下来就能开，不需要联网装包 |
| **大模型** | OpenAI 兼容协议（实测用智谱 glm-4-plus） | 换供应商只改 `.env` 三个变量，不动代码 |
| **模型可替换性** | 适配器模式（`LLMAdapter` 接口） | 真模型与离线规则桩同一接口 —— 没 Key 也能跑全套测试 |
| **前端** | 原生 HTML + CSS + ES Module | 无构建步骤，避免现场演示因构建失败翻车 |
| **数据层** | 结构化题目图谱（JSON 数据文件） | 每题图谱需教研投入，做成可评审、可版本控制的文件 |
| **测试** | 自研极简测试运行器（97 个用例） | 不引测试框架，保持零依赖 |
| **评测** | 19 个教研标注场景 + 6 项量化指标 | 让"不给答案"从主观判断变成可复现的数字 |
| **部署** | 本地 Node 服务 / Vercel serverless / GitHub Pages | 三种形态共用同一份业务逻辑 |

**架构上的核心主张：模型负责"懂"，代码负责"分寸"。**

```
LLM（观察员）          规则代码（决策者）        守卫（把关者）
──────────────        ──────────────────       ──────────────
学生说了什么           该给几级提示              有没有泄题
落在哪一步             用什么策略                有没有跑题
像哪类错因             允许引用哪些概念          有没有越界
```

**为什么这么切**：如果把"该给几级提示"和"什么算给了答案"交给模型，会出现两个方向的失效 ——
学生一喊难就直接拿到最强提示（等于变相给答案）；或者模型换个说法、给近似值、给公式绕过约束。
这两件事都是确定性问题，必须由代码保证。

**关于用 GitHub 来展示 —— 我认为这是目前最合适的方式，理由有三：**

1. **可信度来自可复现，而不是来自描述。**
   别人不用相信我的总结，`clone` 下来跑一条命令就能看到 97 个测试通过、泄题率 0%。
   这比任何一页 PPT 都有说服力。

2. **演示页可以做得很轻。**
   `showcase/index.html` 是一个**零依赖的单文件网页** ——
   没有构建步骤、不加载任何外部资源，发一个链接对方打开就能看。
   发给企业方或老师时，比传一份 PPT 或 PDF 都方便。

3. **诚实的边界可以被看见。**
   演示页里专门留了一页讲"**还没证明什么**"（教学质量未验证、语料只有 19 个场景、
   跨学科只做了初步验证）。把边界说清楚，反而更容易让对方信任前面的数据。

> 如果你希望改成"只给链接、不暴露源码"，也可以只发布演示页、
> 源码留在私有仓库 —— 这套结构支持两种做法，切换只需改一个设置。

## 四、不足与需要改进的地方

### 4.1 验证深度不足（最需要补的一项）

| 问题 | 现状 | 影响 |
|---|---|---|
| **教学质量未经人工验证** | 目前所有指标测的都是"安全"（有没有泄题、有没有越级），**没有一个指标测"有用"** | 无法回答"这个提示到底有没有帮到学生" |
| **评测场景只有 19 个，且是人工编写的** | 15 物理 + 4 数学 | 只能证明"框架对了"，**不能证明能应对真实学生** |
| **长会话未验证** | 场景集最长 3 轮 | 不知道 10 轮以上会不会重复、失忆、层级混乱 |
| **只测了一个模型** | 仅智谱 glm-4-plus | 换模型后的表现未知，无选型依据 |

**改进计划**：
- 抽样 20 轮真实对话请教研盲评，只问三个问题：① 提示是否准确指向卡点？
  ② 学生看完还得自己动脑吗？③ 换成人类老师会说得更多还是更少？
- 用真实学生解题记录把场景集扩到 50+。**这是目前最需要企业支持的一件事。**

### 4.2 功能缺口

| 缺口 | 原因 | 估时 |
|---|---|---|
| 拍照识题（proposal ①） | 需要视觉模型（qwen-vl / glm-4v）；**已给出补法，但未伪造结果** | 约 0.5 天 |
| 实时笔迹观测（proposal ③） | 依赖摄像头/点阵笔硬件，proposal §三.2 已列为需企业支持 | 待设备能力明确 |
| 学科可视化（proposal ⑤） | 受力分析图、动态模型未做 | 待定 |
| 举一反三推荐题（proposal ⑥） | 题库只有 6 题，自动选题没有意义 | 待题库扩充 |
| 题库规模 | 6 题（5 物理 + 1 数学）。**每题图谱需教研投入，是主要成本项** | 教研投入决定 |

### 4.3 工程与部署层面的已知限制

| 限制 | 说明 |
|---|---|
| 公网 Demo 的会话会丢 | serverless 冷启动会清空内存中的会话，间隔久了学习报告页会提示失效（已做友好降级） |
| 会话无持久化 | 当前存进程内存，重启即清空。生产化需接入带学生 id 的存储 |
| 无鉴权、无限流 | 本地开发用的小服务，不适合直接承载真实流量 |
| API 限流敏感 | 实测一次评测耗时在 88 秒到 1925 秒之间波动，生产环境需要请求排队与退避重试 |
| 离线桩能力有限 | 它的价值是"验证护栏与流程"，无法处理真实学生的多样化表达 |

### 4.4 方法论层面的两条教训

1. **测试数据必须来自真实语料。**
   最初的单元测试用例是从规则表原文抄的，天然匹配 ——
   所以 44/44 全绿，而真实评测的错因命中率是 **0%**。这是"测试数据太干净"导致的假通过。

2. **评测必须跑真模型。**
   本周 8 个问题里有 3 个**只有真模型才会暴露**：
   定位被模型误判拉偏（命中率仅 72.7%）、
   模型用"合规的方式"说出答案（无公式无数值，原 6 类检查全部放行）、
   以及我们自己留下的一条"学生声称算错就能拿最强提示"的捷径。

## 五、三句话说明我的工作

**第一句**：我做了一个 AI 老师，你把解题思路说给它听，它能看出你卡在哪一步 —— 但它绝不告诉你答案，只会问你"这个公式成立需要什么条件？"这类问题，逼你自己想出来。

**第二句**：为了保证它真的不给答案（而不是我们嘴上说说），我在它开口之前加了一道"安检" —— 每条提示都要过 7 道检查，凡是出现答案数字、解题公式、或者"所以答案是…"这种话，就拦下来重写。我用真实模型测了 39 轮，它曾经有 9 次想越界，全被拦住了。

**第三句**：现在这套东西已经放到 GitHub 上了，别人打开链接就能看演示，也能自己下载跑一遍看到 97 个测试全部通过 —— 但我最想说的其实是它的不足：**现在的数据只能证明"它守得住不给答案"，还证明不了"它的提示对学生真的有用"**，这件事得请教研老师实际看 20 轮对话才能判断。
