# 图片识别可行性评估（阿里云 OCR）

> 结论先行：**工程接通不难，验收才是大头。**
> 本文只回答"难不难、要动哪些文件、风险在哪"。
> 实际接入的结果与实测质量另见 [`06-marketplace-ocr-integration.md`](06-marketplace-ocr-integration.md)。

---

## 一、结论：难度分级

| 环节 | 难度 | 依据 |
|---|---|---|
| 「图像 → 题干文本」落到现有链路 | **低** | 下游已全部建好，OCR 只需产出一段字符串 |
| OCR 适配层（签名/AppCode、错误码、降级） | **中低** | 零依赖下手写签名，一次性工作 |
| 图片预处理与体积控制 | **中低** | 前端压缩 + 服务端读体上限的协调 |
| 识别**质量**验收（公式 / 图形 / 多栏） | **高（真正的风险）** | 不是写代码能解决的，必须用真实拍题样本测 |

**综合判断：只做"能跑通"约 1.5 ~ 2.5 人天** —— 多出来的部分主要是零依赖约束下的
签名实现、错误码归一化与测试/文档，而不是链路本身。

---

## 二、为什么"接通不难"：链路已经站在门口

项目为此预留得非常完整，**只缺"最后一跳"**，下游的守卫、定位、图谱、教师视图全不用动：

| 已有的东西 | 位置 | 说明 |
|---|---|---|
| 前端上传 UI | `public/index.html` | 点击选图 + 拖拽 + 预览，**已经可用** |
| 前端处理函数 | `public/app.js` 的 `handleImage(file)` | 原来只做预览 + 弹"未接"提示；**改这里就是接线的位置** |
| 后端读题接口 | `POST /api/problem/import` | 吃 `{ rawText }`，输出完整结构化题目 + 解析 |
| 读题核心 | `src/core/intake.js` 的 `understandProblem()` | 含 3 条降级路径、指纹兜底、告警 |
| 题目 id | `fingerprintProblemId()` | 题干内容哈希 ⇒ **同一张图重复识别会命中同一道题** |
| 接口契约 | `src/core/types.ts` 的 `LLMAdapter` | 有"可选能力 + 自动降级"的成熟范式可抄 |
| 配置读取 | `src/core/env.js` 的 `loadEnvFile()` | 通用 KV 读取器，加新 Key **不用改代码** |

## 三、阿里云侧选型

### 首选：`RecognizeEduQuestionOcr`（题目识别）

| 项目 | 事实 |
|---|---|
| Product / Action | `ocr-api` (2021-07-07) / `RecognizeEduQuestionOcr` |
| 定位 | 官方自研，专为「扫描、拍照场景的题目识别」设计 |
| 公式 | **支持印刷体文本与公式的 OCR**；`content` 里公式为 LaTeX |
| 图形 | **检测题目配图并返回坐标**（`figure` 数组） |
| 传图 | `Url`（≤2048 字节，不支持 base64）或 `body`（二进制，≤10MB） |
| 限制 | 长宽 >15px 且 <8192px；长宽比 <50；二进制 ≤10MB；建议 <1.5MB |
| 格式 | PNG / JPG / JPEG / BMP / GIF / TIFF / WebP，**不支持 PDF** |
| 前置 | 控制台须先开通「教育场景识别」服务 |

**为什么不用通用 OCR**：通用文字识别对**公式**基本无能为力，会把分式、上下标、根号拍平成
乱序文本。物理/数学题干里公式就是题意本身，压平之后读题链路拿到的是一段错话 —— 而且
**它不会报错**，只会让图谱悄悄变差。这正是本项目最忌讳的失败模式。

### 备选与不做

| 方案 | 评价 |
|---|---|
| `RecognizeEduPaperOcr`（整页试卷） | 多题场景用；我们是单题导入，用不上且更贵 |
| `RecognizeEduFormula`（公式识别） | 只识别公式，无法承担整题转录 |
| 通用 OCR 打底 | ⚠️ 会静默丢公式，不建议单独使用 |
| **Qwen-VL / qwen-vl-max（百炼）** | 一张图一次调用同时拿到公式与图形语义描述；与现有 LLM 配置同源。代价：按 token 计费、延迟更高 |
| 手写步骤识别 | **另一个数量级的问题**，见 §六 |

**建议**：先用 `RecognizeEduQuestionOcr` 打通，**保留 VL 作为"图形语义说明"的补充通道** ——
OCR 只能给出图形坐标，给不出"图里画了什么"。

## 四、要动的文件与工作量拆解

| # | 文件 | 动作 | 预估规模 |
|---|---|---|---|
| 1 | `src/core/ocr.js` | **新建** | ~150–200 行：调用 + 错误归一化 + **离线降级**（没配 Key 时给明确提示，绝不伪造结果） |
| 2 | `src/server/router.js` | 新增 `POST /api/ocr` | ~40 行 |
| 3 | `src/server/router.js` | 读体体积上限**按路由分档**（`/api/ocr` 为 `2_600_000`，其余 `1_000_000`） | 1 行 |
| 4 | `public/app.js` | 改 `handleImage` | ~60 行：压缩 → 调接口 → **回填 `#stem-input` 而不直接导入** |
| 5 | `public/index.html` | 改文案 | ~15 行 |
| 6 | `.env` / `.env.example` | 新增配置 | ~15 行（`env.js` **不用改**） |
| 7 | `src/server/server.js` | 启动日志加一行 OCR 可用性（脱敏） | ~8 行 |
| 8 | `test/ocr.test.js` | **新建** | ~120 行：签名/契约、错误码、无 Key 降级、**不泄密** |
| 9 | `test/run.js` | 注册 `ocr` 套件 | 1 行 |
| 10 | `README.md` / `docs/周报.md` | 同步用例数字 | ~30 行 ⚠️ `test/docs.test.js` 会核对总量 |

**零依赖约束下的关键判断**：

- 官方 V3 签名是 `HMAC-SHA256` + `x-acs-*` 头，**Node 内置 `node:crypto` 完全够用**，
  不需要引入 SDK —— 符合本项目"clone 下来 `node` 就能跑"的核心约束。
- 二进制传图需把图片字节的 SHA256 放进 `x-acs-content-sha256`，
  **这是唯一需要仔细写、仔细测的地方**（签名错表现为 `SignatureDoesNotMatch`，与"Key 错"不同）。
- 走服务端调用，AK/SK **绝不能进前端**（`test/ui.test.js` 有专门的密钥不外泄断言）。
- `api/index.js`（公网 Demo）建议强制关闭 OCR，否则公开链接会带着额度裸奔。

## 五、真正的风险（不是代码，是质量与口径）

按"最容易被低估"排序：

1. **公式识别质量 = 读题质量的上限。** 指纹是**正则**；OCR 输出的 LaTeX 带空格
   （实测 `1 2 0 ^ { \circ }`），指纹按紧凑写法生成就匹配不上 ⇒ **守卫静默失效**。
   这是必须专门测的一条。
2. **多栏 / 小问排版会被打乱。** 官方返回样例里两道题的文本被交错拼接；
   试卷剪裁不干净时会串题。
3. **图形信息丢失，题干会"缺一个条件"。** OCR 给的是坐标不是语义；含图题若图没进题干，
   学生看到的题干就少一整个条件，而引擎照常建档、照常给提示，**不报错**。
   这是**产品上最需要确认**的一条。
4. **OCR 错误会被下游放大成"AI 没看懂题"。** 所以**必须保留人工可编辑这一环**：
   识别结果先回填文本框、让学生瞄一眼再点"读懂这道题"。这把"OCR 错误"从**故障**降级为
   **可修正的输入**，是投入产出比最高的一条防线。
5. **服务端读体上限（`/api/ocr` 2.6MB，其余 1MB）**：手机原图动辄 3–8MB，不做前端压缩一定 413。
6. **题干哈希的副作用**：学生手改一个字 → 哈希变化 → 重新建图谱 → 多花一次 LLM 调用。
   可接受，但要在教师视图/日志里看得出来。
7. **计费与配额**：需先开通「教育场景识别」并购买/领取题目识别资源包。
   **具体单价与免费额度以阿里云当前计费文档为准** —— 本评估不引用可能过期的价格数字。

## 六、一条重要的边界：这是"题目识别"，不是"手写步骤识别"

| | 题目识别（本次要做） | 手写步骤级识别 |
|---|---|---|
| 输入 | 一张印刷体题图 | 学生书写过程的**时间序列** |
| 输出 | 一段题干文本 | **有序步骤流**（第几步写了什么、哪步涂改、哪步停顿） |
| 阿里云能不能给 | ✅ 专用 API 直接可用 | ❌ **OCR 产品线给不了**，需摄像头/点阵笔 + 动作识别 |
| 难度 | 低 | 高一个数量级 |

**不要把这两件事混在一个排期里。** 本次接入不会顺带解决"卡点识别"的数据来源问题。

---

## 七、建议的推进顺序

1. **先打通、可回退**：`/api/ocr` 返回纯文本 → 回填输入框 → 学生确认后走现有
   `/api/problem/import`。**不做"一键直通"**，把 OCR 错误关在人工确认后面。
2. **拿真实样本定验收口径**：需企业提供 **50~100 张真实学生拍题照片**（含印张、手写批注、
   光照不均、透视畸变），测三个指标：一次成功率 / 公式识别正确率 / 图形信息丢失率。
3. **再决定要不要叠 VL**：若"图形语义"不达标，用 `qwen-vl-max` 补一条"图形说明"通道，
   而不是换掉 OCR。
4. **教师视图加一栏"识别来源"**：让教研能看到题干是**识别来的**还是**粘贴来的** ——
   与"导入题必须暴露图谱是模型生成的"这条设计原则一致。

## 八、需要确认的前提

| # | 事项 | 为什么必须确认 |
|---|---|---|
| 1 | 是否已**开通「教育场景识别」服务** | 未开通会直接报 `UnsupportedService`，与代码 bug 表现相似 |
| 2 | 用主账号 AK 还是 RAM 子账号 | 子账号需 `AliyunOCRFullAccess`；建议权限最小化 |
| 3 | 能否提供真实拍题样本 | 没有样本，§五 1–4 条风险全部无法验收 |
| 4 | 公网 Demo 是否也要开 OCR | 建议比照 LLM Key 强制关闭 |
| 5 | 是否接受"识别结果必须人工确认"这一步 | 影响交互设计与验收标准 |
