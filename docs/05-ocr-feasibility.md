# 图片识别（接入阿里云 OCR）可行性评估

> 结论先行：**工程接通不难，验收才是大头。**
> 本次评估只回答"难不难、要动哪些文件、风险在哪"，不含任何代码改动。
> 基线：`node test/run.js` 当前 **219/219 通过**，工作区干净。

## 一、结论：难度分级

| 环节 | 难度 | 依据 |
|---|---|---|
| 「图像 → 题干文本」落到现有链路 | **低** | 下游已经全部建好，OCR 只需要产出一段字符串 |
| 阿里云 OCR 适配层（V3 签名、错误码、降级） | **中低** | 零依赖项目要手写签名，比装 SDK 重，但是一次性工作 |
| 图片预处理与体积控制 | **中低** | 前端压缩 + 服务端 1MB 读体上限的协调 |
| 识别**质量**验收（公式 / 图形 / 多栏） | **高（真正的风险）** | 不是写代码能解决的，必须用企业真实拍题样本测 |

**综合判断：如果只做"能跑通"，1.5 ~ 2.5 人天。**
与你之前文档里写的"约 0.5 天"相比，多出来的部分主要是**零依赖约束下的签名实现**与**测试/文档**，而不是链路本身。

## 三、阿里云侧选型

### 推荐首选：`RecognizeEduQuestionOcr`（题目识别）

| 项目 | 事实 |
|---|---|
| Product / Action | `ocr-api` (2021-07-07) / `RecognizeEduQuestionOcr` |
| 定位 | 官方自研，**专为「扫描、拍照场景的单选题题目识别」**设计（文档原文） |
| 公式 | **支持印刷体文本与公式的 OCR 识别**；返回的 `content` 里公式为 LaTeX（实测样例含 `1 2 0 ^ { \circ }`、`\angle M O N` 这类形式） |
| 图形 | **会检测题目中的配图并返回坐标**（`figure` 数组，含 type / x / y / w / h / points） |
| 图像增强 | 默认支持自动旋转、畸变矫正、模糊增强、透视畸变、任意背景 |
| 传图方式 | `Url`（图片链接，≤2048 字节，**明确不支持 base64**）或 `body`（图片二进制，≤10MB）二选一 |
| 图片限制 | 长宽 >15px 且 <8192px；长宽比 <50；二进制 ≤10MB；**建议 <1.5MB** |
| 格式 | PNG / JPG / JPEG / BMP / GIF / TIFF / WebP，**不支持 PDF** |
| 前置条件 | 需先在控制台**开通「教育场景识别」服务**；子账号需 `AliyunOCRFullAccess` 或 `ocr:RecognizeEduQuestionOcr` |
| 参考 | [官方接口文档](https://help.aliyun.com/zh/ocr/developer-reference/api-ocr-api-2021-07-07-recognizeeduquestionocr)、[在线调试](https://next.api.aliyun.com/api/ocr-api/2021-07-07/RecognizeEduQuestionOcr) |

**为什么不是通用 OCR**：通用文字识别（RecognizeGeneral / RecognizeAdvanced）对**公式**基本无能为力，会把分式、上下标、根号拍平成乱序文本。物理/数学题干里公式就是题意本身，压平之后读题链路拿到的是一段错话 —— 而且**它不会报错**，只会让图谱悄悄变差。这正是本项目最忌讳的失败模式。

### 备选与不做

| 方案 | 评价 |
|---|---|
| `RecognizeEduPaperOcr`（整页试卷） | 多题场景用；我们是**单题导入**，用不上，且更贵 |
| `RecognizeEduFormula`（公式识别） | 只识别公式，无法承担整题转录 |
| 通用 OCR 打底 | ⚠️ 会静默丢公式，不建议单独使用 |
| **Qwen-VL / qwen-vl-max（百炼）** | 与 [.env.example:14](.env.example#L14) 注释里已有的规划一致，**一张图一次模型调用同时拿到公式与图形语义描述**；好处是与现有 LLM 配置同源、不用新增一套云账号体系。代价：按 token 计费、延迟更高、结果不如专用 OCR 稳定 |
| 手写步骤识别（proposal 3b） | **另一个数量级的问题**，见第六节 |

**我的建议**：先用 `RecognizeEduQuestionOcr` 打通（准确率与成本都可控），**保留 VL 作为"图形语义说明"的补充通道** —— 因为 OCR 只能给出图形坐标，给不出"图里画了什么"。

**技术要点（零依赖约束下的关键判断）**：

- 阿里云 V3 签名是 `HMAC-SHA256` + `x-acs-*` 头，**Node 内置 `node:crypto` 完全够用**，不需要引入 `@alicloud/ocr-api20210707` 等 SDK —— 这符合本项目"clone 下来 `node` 就能跑"的核心约束（见 [package.json](package.json) 的 `dependencies: {}`）。
- 二进制传图若要手写签名，需要把图片字节的 SHA256 放进 `x-acs-content-sha256`，比 JSON 体多一步；**这是本次评估里唯一需要仔细写、仔细测的地方**（签名错会表现为 `SignatureDoesNotMatch`，与"Key 错"的错误码不同，必须区分开）。
- 走服务端调用而非前端直连：AK/SK **绝不能进前端**。项目里已经有一条 `test/ui.test.js` 的断言专门守"密钥不外泄"，新代码必须符合它。
- `api/index.js`（公网 Demo）建议比照现有 `LLM_API_KEY` 的处理（[api/index.js:35](api/index.js#L35)）**强制关闭 OCR**：否则公开链接会带着你的阿里云额度裸奔。

## 五、真正的风险（不是代码，是质量与口径）

按"最容易被低估"排序：

1. **公式识别质量 = 读题质量的上限。**
   `answerFingerprints` / `formulaFingerprints` 是**正则**。OCR 输出的 LaTeX 带空格（实测样例 `1 2 0 ^ { \circ }`），如果指纹按紧凑写法生成，就会**匹配不上** —— 守卫静默失效。这是必须专门测的一条。

2. **多栏 / 小问排版会被打乱。**
   从官方返回样例能看到，两道题的文本被交错拼接。单题拍照问题不大，但**试卷剪裁不干净时会串题**。

3. **图形信息丢失，题干会"缺一个条件"。**
   OCR 给的是图形**坐标**，不是图形**语义**。一道"如图，导体棒在磁场中匀速运动"的题，如果图没进题干，学生看到的题干就少了一整个条件 —— 而引擎会照常建档、照常给提示，**不报错**。
   → 这是我认为**产品上最需要在企业侧确认**的一条。

4. **OCR 错误会被下游放大成"AI 没看懂题"。**
   OCR 错一个数值 → 已知量错 → 提示不对 → 学生认为产品不行。所以**必须保留人工可编辑这一环**：识别结果先回填到文本框、让学生瞄一眼再点"读懂这道题"。这个设计把"OCR 错误"从**故障**降级为**可修正的输入**，是投入产出比最高的一条防线。

5. **服务端 1MB 读体上限**（[router.js:204](src/server/router.js#L204)）：手机原图动辄 3–8MB，不做前端压缩一定 413 或"请求体过大"。

6. **题干哈希的副作用**：学生手改一个字 → 哈希变化 → 重新建图谱 → **多花一次 LLM 调用**。可接受，但要在教师视图/日志里能看出来。

7. **计费与配额**：需先在控制台开通「教育场景识别」并购买/领取题目识别资源包（有免费额度可测试）。**具体单价与免费额度请以[阿里云 OCR 计费文档](https://help.aliyun.com/zh/ocr/product-overview/product-billing)当前页面为准** —— 本评估不引用可能过期的价格数字。

## 六、一条重要的边界：这是"题目识别"，不是"手写步骤识别"

你的汇报文档里已经把这两条链路分开写了（[share/汇报_技术进展与需求清单.md:160](share/汇报_技术进展与需求清单.md#L160)），本评估确认这个划分是对的：

| | 题目识别（本次要做） | 手写步骤级识别（proposal 3b） |
|---|---|---|
| 输入 | 一张印刷体题图 | 学生书写过程的**时间序列** |
| 输出 | 一段题干文本 | **有序步骤流**（第几步写了什么、哪一步涂改、哪一步停顿） |
| 阿里云能不能给 | ✅ 专用 API 直接可用 | ❌ **OCR 产品线给不了**，需要摄像头/点阵笔 + 专门的动作识别能力 |
| 难度 | 低 | 高一个数量级 |

**不要把这两件事混在一个排期里。** 本次接入不会顺带解决"卡点识别"的数据来源问题 —— 那个仍然依赖企业侧的硬件与识别能力。

## 七、建议的推进顺序

1. **先打通、可回退**：`/api/ocr` 返回纯文本 → 回填输入框 → 学生确认后走现有 `/api/problem/import`。**不做"一键直通"**，把 OCR 错误关在人工确认后面。
2. **拿真实样本定验收口径**：需要企业提供 **50~100 张真实学生拍题照片**（含印张、手写批注、光照不均、透视畸变），测三个指标：
   - 一次成功率（识别出的题干能直接读懂，不需手改）
   - 公式识别正确率（分式 / 上下标 / 根号 / 希腊字母）
   - 图形信息丢失率（含图题中，图意是否缺失）
3. **再决定要不要叠 VL**：若"图形语义"这一项不达标，用 `qwen-vl-max` 补一条"图形说明"通道，而不是换掉 OCR。
4. **教师视图加一栏"识别来源"**：让教研能看到这道题的题干是**识别来的**还是**粘贴来的**，以及识别置信信息 —— 与现有"导入题必须暴露图谱是模型生成的"这条设计原则一致（[registry.js:137](src/core/registry.js#L137)）。
