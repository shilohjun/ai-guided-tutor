# yangshuhan分支：给第一次协作的同学

你的分支不是一个需要手动复制文件的空文件夹，而是一条独立的修改记录。我们检查时，yangshuhan与main原本都指向同一版本b76e525e5dec90be1c3692089e64e3dd12ab1f08，因此已经有主分支全部内容，不需要手动再复制。

## 这次怎么做

在yangshuhan的现有项目上直接修改对应文件，新增文件也放这里。上传后组员可以切换到yangshuhan查看，或通过Pull Request对比改动。没有必要只上传新增文件，更不要把全项目另存成一套重复目录。

Pull Request可理解为“请组员审阅这一批改动”的申请。创建它本身不会修改main；点击Merge才会合并。因此此次只提交个人分支，不自行合并。

## 以后用GitHub网页更新

1. 打开仓库，点文件列表上方的分支选择框，明确选择yangshuhan。
2. 修改已有文件：打开文件，点编辑按钮；新文件用Add file上传或创建。保持原目录结构。
3. 提交前确认页面显示提交到yangshuhan，写清改了什么、为什么改，如“统一提示字数，补充三级范例”。
4. 在Pull requests中建立从yangshuhan指向main的草稿申请，说明改动、测试和未解决问题。已有同一分支申请时，后续提交会自动进入该申请，不必重复创建。
5. 发分支或申请链接给组员讨论，由团队确认是否合并。main不要用个人修改直接覆盖。

## main后面有了组员的新内容怎么办

不需要每次重建个人分支。先把最新main合入yangshuhan，再继续个人修改；有冲突说明同一位置双方都改过，需要对照保留，不能直接全部覆盖。GitHub申请页有时会提供更新分支按钮；没有按钮或出现冲突时，让负责代码的组员帮忙同步即可。

分支同步与合并个人改动进main是不同方向：前者更新你的工作基础，后者发布你的改动。不要在尚未审阅时点Merge，也不要用强制覆盖推送来解决冲突。

## 一次提交该放什么

相关源码、提示词规范、案例说明、测试与必要使用文档可以一起提交。API密钥、.env、本地日志、缓存、依赖目录与个人临时文件不要上传。每次提交围绕一件事，组员更容易看懂和回退。
