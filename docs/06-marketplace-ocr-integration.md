## 一、实测确认的契约（不是猜的）

| 项目 | 值 | 验证方式 |
|---|---|---|
| 调用地址 | `https://mquestion.market.alicloudapi.com/ocrservice/mathQuestion` | 真实调用 HTTP 200 |
| 请求方式 | POST，`Content-Type: application/json; charset=UTF-8` | 契约 + 真实调用 |
| 认证 | `Authorization: APPCODE <AppCode>` | 真实调用 |
| 请求体 | `{"img":"<纯base64>","prob":false,"rotate":false}` | 真实调用 |
| 图片限制 | base64 后 ≤4M；最短边 ≥15px；最长边 ≤4096px；jpg/png/bmp | 契约 |
| 成功响应 | `{"content":"整段题干…","figure":[…]}` | **实测** |
| 失败响应 | `{"error_code":400,"error_msg":"…","requestId":"…"}` | **实测** |

### 三个"写错就必然失败"的细节

1. **请求体是 JSON，不是表单。** 云市场多数接口用 `x-www-form-urlencoded`，这一个偏偏是 JSON ——
   用表单提交会得到参数错误。
2. **图片字段名是 `img`，值是纯 base64，不能带 `data:image/jpeg;base64,` 前缀。**
   而 ShowAPI 系通用 OCR **正好相反**（要求带前缀）。
3. **没有 `showapi_res_code` / `ret_code` 信封** —— 是扁平结构，错误用 `error_code` / `error_msg`。
   原先按云市场通用形态预设了解析，**第一次真机测试就被纠正了**。

> 这三条都是"看起来一样、错了不报错只失败"的细节，已全部固化成断言（`test/ocr.test.js`）。

### 一个可复用的排查经验（网关状态码的含义）

| 请求 | 结果 | 含义 |
|---|---|---|
| 某路径 + 正确 AppCode | **401** | 路径存在、AppCode 被网关认了，但未授权 |
| 同地址 + 乱写 AppCode | 404 | 不存在的路径 |
| 不带认证头 | 400 | 网关要求认证 |

**判据**：404 = 路径不存在（不计费，可放心试）；**401 = 路径存在但未授权**（最有价值的一档，
它同时证明域名对、路径对、AppCode 有效）。这把一次要烧调用次数的探索变成了零成本探索。

## 二、实测识别质量（真实样题，含公式与单位）

输入是一张 1100×620 的印刷体题图（含 Ω / m/s / 上下标）。识别文本**原样**如下（未清洗）：

```
如图所示，水平放置的两条光滑平行金属导轨间距为 \mathsf{L}=0.5\；\mathsf{m}，处于竖直向上的匀强磁场中，
磁感应强度 \mathsf { B } = 0 . 4 \： \mathsf { T } _ { \circ } ，导轨左端接有 电动势 \mathsf{E}0\，=\，1.5\，\mathsf{V}、
内阻 \mathsf{r}=0.1~Ω 的电源，右端接有阻值 \mathsf{R}=0.3\：Ω 的电阻。一根质量 \mathsf{m}=0 .2kg的导体棒…
求：(1)导体棒中的感应电流Ⅰ的大小和方向； (2)水平外力F的大小； (3)外力做功的功率P。
```

**下游效果（关键）**：这份带 LaTeX 噪声的文本直接进读题链路，
**6 步路径 / 6 条关键条件 / 0 告警 / 图谱可用**，知识点识别正确（电磁感应、法拉第电磁感应定律、
安培力、闭合电路欧姆定律、功率）。
**也就是说：OCR 的格式噪声被读题模型吸收了。** 这验证了"两段式"的设计选择 ——
OCR 只负责"把图变成字"，理解交给专门做理解的模型。

### 三条真实缺陷（都不报错，只让结果悄悄变差）

| # | 现象 | 影响 | 应对 |
|---|---|---|---|
| 1 | **下标丢失**：`E0 = 1.5 V`（原文是 E₀） | 已知量符号不精确，不影响读题 | 人工确认环节可见；不必自动纠正 |
| 2 | **LaTeX 带空格噪声**：`0 . 4`、`\mathsf { B }`、`0.1~Ω` | ⚠️ **直接影响指纹正则匹配** —— 指纹按紧凑写法生成就匹配不上，守卫**静默失效** | 见下方"待办" |
| 3 | **图形未被检测**：题图有人工配图，但 `figure` 返回 0 处 | 含图题的几何条件丢失，而引擎照常建档、不报错 | 已知风险，见 `docs/05` §五第 3 条 |

> 第 2 条最有价值：它在 05 文档的风险清单里被列为"必须专门测的一条"，现在有了实证。
> **建议**：`intake.js` 生成指纹时对文本做一次归一化（去空格、统一 `\mathsf{}/~/\；` 等噪声），
> 否则"OCR 来的题"守卫强度低于"粘贴来的题"。

## 三、这是两套完全不同的接入方式（务必分清）

| | 官方 POP 接口 | **云市场商品（本项目采用）** |
|---|---|---|
| 标识 | `Product=ocr-api` `Action=RecognizeEduQuestionOcr` | `cmapi00043052` |
| 鉴权 | AccessKey + **V3 签名**（HMAC-SHA256） | **AppCode 简单认证** |
| 凭据形态 | AK/SK 一对 | **一个 AppCode 字符串**（不是 AppKey！） |
| 请求体 | JSON 或二进制 body | JSON（由服务商定义） |
| 要不要手写签名 | 要（约 60~80 行） | **不要** —— 一个请求头就完了 |

**好消息**：你选的这条路**工程上更简单** —— 原本"中低难度"的手写 V3 签名直接消失了：

```
Authorization: APPCODE <你的AppCode>
```

> 官方文档提醒：AppCode 是明文传输，**必须走 HTTPS**，且**只能放服务端**，绝不能下发到浏览器。

### 术语更正：要的是 AppCode，不是 AppKey

| 名称 | 用途 | 怎么来的 |
|---|---|---|
| **AppCode** | 简单认证（云市场商品**默认用这个**） | API 网关控制台 → 调用 → 应用管理 → App 详情页 |
| AppKey + AppSecret | 摘要签名认证（另一条路，要自己算签名） | 同一页面的密钥对 |

⚠️ 如果你说的"appkey"其实指 **ShowAPI（万维易源）控制台**里的 `appKey`，
那说明你买的是 **第三套**接入方式（域名 `https://route.showapi.com/...`），请先确认控制台里看到的是哪个。

## 四、明白的两类"云市场 OCR"返回形态（探测脚本可自动识别）

```jsonc
// 形态 A：ShowAPI 风格信封（万维易源系，最常见）
{
  "showapi_res_code": 0,          // 系统级：0 = 请求通了（≠ 业务成功！）
  "showapi_res_body": {
    "ret_code": 0,                // 业务级：真正看这个
    "str": "识别出的整段文字",
    "list": [ { "text": "...", "confidence": 0.996, "text_region": [[373,40],…] } ]
  }
}
```

对写适配器很关键的几点：

- **先判 `ret_code` 再取文本**：`showapi_res_code=0` 只代表通道通了，业务可能失败而 `str` 为空。
- `list` 与 `str` **由 `need_all_region` 决定返回哪个**，不要写死同时取。
- 常见业务错误码（用于给用户**人话**提示）：`10` 参数错误 · `20` 文件格式错误 ·
  `40` 文件下载失败 · **`50` 文件内容过大** · `60` 图片解析失败 · `70` OCR 识别失败 ·
  `80` 服务超时 · `90` 识别异常。
- **体积上限比官方接口小得多**（base64 ≤0.7MB / URL ≤1MB，建议像素 < 1200×1200）——
  前端必须压缩。

> ⚠️ 这是**同家族产品**的形态，不等于本项目那个商品的确切形态；以实测为准。

## 五、接入设计

```
浏览器                          服务端                        云市场
  │  选图 / 拖拽 / 拍照
  │  canvas 压缩到长边 ~1600px、quality 0.85（超过 1.5MB 直接不发请求）
  ├── POST /api/ocr  { image: dataURL } ──►│
  │                                        │ 体积/格式前置校验
  │                                        ├── POST + APPCODE 头 ──►│
  │◄── { rawText, figures?, latencyMs, provider } ──┤
  │
  │  ★ 回填到 #stem-input，**不自动导入**
  │  ★ 学生看一眼 / 改错字，再点「读懂这道题」
  └── POST /api/problem/import { rawText } ──►（既有链路，一行不改）
```

**为什么坚持"回填 + 人工确认"而不是一键直通**：OCR 错一个数值 → 已知量错 → 提示全错 →
学生会认为产品不行。这一步把 OCR 错误从**故障**降级为**可修正的输入**，
是整个接入里性价比最高的一条设计。

### 三个只有"真起服务"才暴露出来的坑（已修，均有断言守着）

1. **`req.destroy()` 会让 413 变成"网络错误"。** 超限时先 destroy 再写响应 ⇒ socket 在响应
   发出前被掐断 ⇒ 客户端看到 `fetch failed`，学生会以为网络不好反复重试 —— 而每次都在烧调用次数。
2. **`req.pause()` 会死锁。** 客户端在等响应、服务端在等 body。正确做法：**继续读完但一个字节
   都不再存**。
3. **预设的返回信封是错的。** 按云市场通用形态（`showapi_res_code` / `ret_code`）写的解析，
   在真实响应（扁平 `content` / `error_code`）面前会**静默失败** —— 表现为"识别成功但输入框是空的"。

> 这三条的共同特征：**不报错，只让产品悄悄变差。**
