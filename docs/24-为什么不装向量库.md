# 为什么不装向量库（833 题这个量级）

## 一句话

**833 道题、每题 259 字，向量库解决的是"百万级数据、需要持久化与增量更新"的问题 —
在这个量级上它是负优化：多一个服务、多一份运维、多一次网络往返，换来的是更慢和更糊。**

## 算给你看

| 项 | 数字 |
| --- | --- |
| 题量 | 835（去重 833） |
| 一条 embedding（bge-small-zh，512 维，float32） | 2 KB |
| 全库矩阵 | 833 × 512 × 4B ≈ **1.7 MB** |
| numpy 暴力点积一次查询 | **< 1 ms** |
| 向量库（Qdrant/Chroma）一次查询 | 网络往返 + 服务端检索，通常 5–20 ms |

1.7 MB 直接躺内存里，全量重算一次余弦相似度比一次 HTTP 往返还快。
**在这个规模上引入向量库，是把"一次矩阵乘法"换成"一次 RPC"。**

## 那什么时候该装

| 条件 | 说明 |
| --- | --- |
| 数据量 ≳ 10 万条 | 暴力检索开始变成瓶颈（10 万 × 512 约 200 MB） |
| 需要持久化与增量更新 | 题在持续增删，不能每次重启重算 |
| 多进程/多实例共享索引 | 每个实例各自 200 MB 不划算 |
| 需要按元数据过滤 + 向量混合检索 | 向量库的过滤能力比手写 mask 好用 |

## 但 embedding 值得试

**不装向量库 ≠ 不用 embedding。** 833 条向量装进 `np.ndarray`，
用 numpy 点积检索，零新增服务。这是本项目要做的对照实验：
词法 top-1 是 36.5%，embedding 若上不了 45%，就不引入模型依赖。

## 如果面试问"你为什么不用向量库"

答：我用**留出法**量过词法基线（top-3 65%、top-5 74.3%），也量过 833 条的暴力检索成本（<1ms）；
在这个量级上向量库的收益是负的。要证明"用过"，我会做的是同一个接口下的两种实现跑同一批查询
（numpy 暴力 / Qdrant HNSW）出延迟与召回对照表 —— 而不是为了简历把生产切过去。
